# Planner lessons

One line per task: what the worker got wrong or what slowed it, and the spec gap behind it.
**Read this before writing every spec.** Add a line after every delegated task.

- A-10 · The worker stopped silently (exit 0, nothing written) when it tried a command not in `opencode.json`'s allow list. → Give the exact commands in the prompt (`cd services/api && ../../.tools/bin/uv.exe run pytest -q`); never rely on it choosing allowed ones.
- A-10 · The spec said "add `supabase_url`" but the setting already existed; the worker noticed and adapted. → Before writing a spec, `grep` that each name I ask it to add does not already exist.
- A-10 · Two follow-ups were not in the spec (close the client on app shutdown, percent-encode keys), so they were not done. → Ask "who calls `aclose` / who owns the lifecycle?" for every resource the task creates.
- A-10 · Worker added no tests beyond the 7 listed, and all 7 were real. → Numbered test cases with concrete inputs/outputs work; keep that format.
- A-10b · The dry run (read-only worker plan) found 4 spec problems I had missed, one a safety hazard: tests that call `create_app(settings)` can read `MONET_DATABASE_URL` from the environment and run migrations on a real DB. → Every test that builds the app must null `database_url` and `supabase_*` via `model_copy`. Always do the dry run; it costs nothing.
- A-10b · Two of my five tests passed before any change (vacuous). → For each test ask "does it fail on the old code?" If not, rewrite it or label it a regression guard.
- A-10b · Bookkeeping was unspecified (does the worker edit BACKLOG/PROGRESS, which files go in the commit, may it stage `opencode.json`?). → List the spec file (Worker report) under "Files to edit", say who updates BACKLOG/PROGRESS, and name the exact files for the commit.
- A-10b · After two dry runs the worker succeeded first try, one commit, exactly the 4 listed files. Mutation check (old src + new tests): 3 of 6 tests fail as they should; "round trip with `ü`" passes on old code because httpx already encodes by itself. → Run the mutation check (`git checkout HEAD~1 -- <src files>`, run tests, restore) on every task, and in specs only call a test a regression test if the OLD code fails it.
- A-10b · Independent Sonnet-low review (~13 s, ~47k tokens) found no blocker; both findings were already accepted spec decisions (no try/finally; store not reusable). Useful as a cheap second opinion, but it only sees the diff, so it cannot find gaps the spec itself has.
- harness · Headless OpenCode ends the whole run on any permission prompt ("ask" is auto-rejected). `"*": "deny"` on bash plus `"external_directory": "deny"` turn those into recoverable errors; the worker adapts and carries on.
- A-17 · The dry run found 6 gaps in my spec (does the check run on 2xx too? does the body override the HTTP status? helper placement contradicted itself; one numbered test held two scenarios; the no-leak assertion covered only the key). After fixing them the worker succeeded first try, one commit, three listed files. Mutation check: tests 1-2 fail on old code, the three labelled guards pass. → For any "classify a response" rule, state which statuses it applies to and whether it runs on success; one scenario per numbered test; list every string a message must not contain.
- harness · A git worktree has none of the gitignored folders the tooling needs (`.tools`, `data/generated`, `apps/android/local.properties`). `scripts/lane.ps1 -Name x -Branch y` creates the lane and links them (`-Remove` deletes it; it unlinks junctions first so the shared toolchain is never deleted). Paths in specs are relative to the lane root.
- A-14 · The dry run found three failure-mode gaps in my spec (an `expire` failure leaking keys, the clock read twice, no Redis timeout) and the worker then succeeded first try. → For every external call in a spec, write what happens when the dependency is down, slow or half-failing: the timeout, which errors are swallowed, and that the 429 itself is never inside a `try`.
- F-19a · Build scripts have no unit-test seam, so I wrote the tests as commands with exact expected output; the worker passed all of them first try. It could not test the tag path (no tags exist, `git tag` is not in its allow list), so the planner checked it with a temporary tag and `aapt2 dump badging` on the built APK. → For build logic, give command + exact output as the test, and list in the spec what the planner verifies afterwards.
- F-19a · The independent review flagged two things the spec never covered (shallow clones, `-dirty` suffix). → When a value derives from git state, write the CI/clone requirements into the spec or PROGRESS.
- F-20 · I coded the sign-out UI myself instead of delegating; the user objected. → The planner never writes feature code. Even a 3-file change goes through a spec, because the point of the workflow is saving planner quota and keeping an independent check.
- F-19b · The dry run caught a design flaw in my spec: splitting every variant would have changed the debug APK path that the emulator workflow installs. Worker then succeeded first try (5 files). → For any build-output change, ask "which existing workflow depends on this file name or path?" and restrict the change to the variant that needs it.
